# What can WordPress's REST API hold as Pulpit's system of record?

Research for thomasfosterau/pulpit#414. Today `pulpit-wordpress` **serves** a `wp/v2` read API over the kernel (docs/wordpress.md). The new idea runs the other way: the kernel's seams are filled by a real WordPress site, read and written over its REST API. This note maps each kernel capability onto what core WordPress offers, for reading and writing.

**Baseline.** WordPress core `trunk` at `7.2-RC2-65605-src` (from `src/wp-includes/version.php`), read on 2026-11-20 from `WordPress/wordpress-develop`, plus the developer.wordpress.org handbooks. "Core" means no plugins. Some rows depend on PHP on the WordPress side (`register_post_type`, `register_meta`, `register_taxonomy`, filters). A REST client can't register any of these, so they're marked **needs a site plugin**. Line numbers refer to the trunk files listed under [Sources](#sources).

**Legend.** **Full**: the kernel's contract holds. **Partial**: it works, and the cell says what's lost. **None**: core has nothing for it, and the cell names the workaround if there is one.

## Summary

- **WordPress keeps one mutable row per post.** It has no head/live split and no version counter. History is a side effect of saving: a revision is recorded only when title, content, excerpt or opted-in meta change. Revisions can be capped, turned off or deleted. A WordPress-backed chain is therefore lossy best-effort history. It can't be the kernel's append-only chain (`VERSION-CHAIN-001/002`).
- **Core has no optimistic concurrency.** No REST controller or the REST server reads `If-Match`, `If-Unmodified-Since` or `ETag`, and nothing answers `412`. A compare-then-write on `modified_gmt` is possible, but it has a race window and only one-second precision. A single update isn't atomic either: the post row, its terms, its meta and any additional fields are written in separate steps.
- **The publishing basics fit well:** posts and custom types, terms, comments and their moderation, author, `private` / password visibility, scheduling (`future`), trash, media upload with server-made sizes, and per-user autosaves.
- **Locales, public reactions, generic edges, albums, audiences, proposals and the live pointer are missing from core.** Core 7.2 does add reactions, but only on editorial notes.
- **Auth is Application Passwords** (Basic auth, HTTPS only by default, no scopes) or cookie plus nonce. A system-of-record client would run as one privileged service account, so the kernel's own read gates must stay in front of it.

## Concurrency

- **No HTTP preconditions.** A search of `class-wp-rest-server.php`, `rest-api.php` and the posts, revisions, autosaves, attachments, comments, terms and search controllers finds no `ETag`, `If-Match`, `If-None-Match`, `If-Unmodified-Since` or `412`. Every `update_item` writes whatever it is sent: last writer wins.
- **The post lock is advisory and only partly applies.** `_edit_lock` (`wp_check_post_lock`) is the editor's heartbeat lock. Among REST routes only the autosaves controller reads it (`autosaves-controller:228-232`), to decide between updating the draft and storing an autosave revision. The posts controller's `update_item` never checks it (`posts-controller:943-1060`).
- **A single update is not atomic.** `update_item` calls `wp_update_post`, then the format, `featured_media`, sticky flag, template, terms, meta and additional fields one after another. A failure partway (for example in `meta->update_value`) returns an error after the post row is already saved (`posts-controller:978-1040`).
- **The nearest stand-in is compare-then-write on `modified_gmt`, or on the newest revision id.** Read the value, write, and check that the response's previous state matches. That leaves a race window, and `post_modified` has one-second precision (MySQL `DATETIME`), so two writes in the same second can't be told apart. A strict precondition needs a site plugin, for example a `rest_pre_dispatch` / `rest_pre_insert_{type}` filter that compares an `If-Match` with a version counter in meta. The read and write still aren't serialised unless the plugin takes a row lock or `GET_LOCK`.
- **Real-time collaboration is not in core.** The Yjs / HTTP-polling sync work was removed from WordPress 7.0's scope before RC3 (make.wordpress.org, 2026-04-01). Trunk (7.2-RC2) has no `wp-includes/collaboration/` and registers no sync controller in `rest-api.php`.

## Auth

- **Application Passwords** (core since 5.6) are sent as HTTP Basic auth. By default they're available only when `is_ssl()` or the environment type is `local` (`user.php:5202-5225`), and they work only on API requests, REST or XML-RPC (`user.php:386-400`). They have **no scopes** (the integration guide lists scoping as future work), so a password acts with its user's full capabilities. There's a browser flow for a user to approve an app (`/wp-admin/authorize-application.php`, with `success_url` over `https` or an app scheme), and revocation and management are under `/wp/v2/users/{id}/application-passwords`.
- **Cookie plus nonce** (`X-WP-Nonce`, action `wp_rest`) works only for same-origin, logged-in browser use. Without the nonce the request runs as user 0.
- **Plugins** offer OAuth 1.0a and JWT. The Basic-Auth-with-real-password plugin is for development only.
- **Consequences for Pulpit.** A backend adapter would authenticate as one service user, holding at least `edit_others_posts`, `publish_posts`, `upload_files`, `moderate_comments`, `assign_terms` and, to avoid kses rewriting content, `unfiltered_html`. Reads would use `context=edit`, which returns raw fields and drafts and so bypasses WordPress's per-viewer rules. Pulpit's own read gates (`SEC-AUTH-ENUM-001`) must stay authoritative, and WordPress's capability checks protect only against the adapter itself.

## Implications for the backend-capability ticket

- Treat WordPress as a **mutable store with advisory history**, not a chain. Have the kernel's chain contract degrade explicitly (`expectedVersion` best-effort or refused, `history` lossy) rather than pretend.
- A **site-side companion plugin** is the realistic baseline for a usable backend: custom types, taxonomies and meta with `show_in_rest`, `revisions_enabled` meta, an `If-Match` precondition, anonymous comments if wanted, and real cron. Core alone gives at best a read-mostly backend.
- Map **integer ids** with the package's existing `IdCodec`, and keep the codec's table in Pulpit, because WordPress ids are assigned on create.
