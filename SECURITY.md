# Security Policy

## Reporting a vulnerability

Please report security vulnerabilities privately via GitHub's [**Report a vulnerability**](https://github.com/thomasfosterau/pulpit/security/advisories/new) button (Security → Advisories), **not** through public issues.

You can expect an initial response within a few days. Please include a description, reproduction steps, and the affected version.

## Supply-chain hardening

This package is published with a hardened, automated pipeline designed to resist supply-chain attacks (e.g. self-propagating npm worms that steal credentials and publish trojanized versions):

- **No long-lived npm token.** Publishing is npm trusted publishing (OIDC) from the protected `release` environment: GitHub Actions proves its identity to npm with a short-lived, workflow-bound OIDC token, so there is no `NPM_TOKEN` secret to steal from CI. The publish step is `pnpm publish`, which performs the OIDC exchange itself.
- **Provenance.** Nothing requests [npm provenance](https://docs.npmjs.com/generating-provenance-statements). npm attaches it only when the source repository and the package are both public; this repository is private, so releases carry none today (see [PUBLISHING.md](./PUBLISHING.md#provenance)).
- **Install scripts disabled in the release job.** The release job installs with `--ignore-scripts`, keeps pnpm from re-installing with scripts before a later `pnpm run`, runs only the workspace's own lockfile-pinned `prepare` step explicitly, and publishes with `pnpm publish --ignore-scripts`; the reasons sit beside each setting in [release.yml](.github/workflows/release.yml). CI installs with scripts, but `allowBuilds` in `pnpm-workspace.yaml` names the only packages whose install scripts may run.
- **Pinned actions.** All GitHub Actions are pinned to full commit SHAs, so a hijacked tag cannot inject malicious workflow code.
- **Supply-chain delay.** `minimumReleaseAge` in `pnpm-workspace.yaml` holds a newly published third-party version for one day before pnpm will install it.
- **Least privilege.** Workflows default to `permissions: {}`; each job opts into only the scopes it needs. CI checks out with `persist-credentials: false`.
- **Manual approval gate.** Publishing runs in a protected `release` environment that requires manual approval.
- **Locked dependencies.** Installs use `pnpm install --frozen-lockfile` against the committed `pnpm-lock.yaml`; Dependabot proposes updates for review.

## Invariant IDs

Code comments, tests and the agent guidance cite these IDs. They are grep handles carried over from the website and gardeneria applications, which have no surviving written definition for most of them, so this table is where each rule is defined for this repository. Each rule is stated as pulpit honours it, derived from pulpit's code and tests and from the apps' citing sources. Paths are under `packages/pulpit/`.

| ID | Rule | Enforced by |
| --- | --- | --- |
| `VERSION-CHAIN-001` | Every edit to a node is a new version written through the chain operations (`defineVersionChain`): create, update, restore, delete and `restoreVersion` all append, and nothing else writes a version row. | `src/version-chain.ts`; `tests/version-chain.test.ts` ("appends at N_max + 1 …") |
| `VERSION-CHAIN-002` | The chain is append-only. Every write lands at `N_max + 1`, no version row is ever updated, deleted or reordered, and a concurrent append colliding on `(id, version)` fails `VersionConflict` and is never retried. | `src/version-chain.ts`; the store's `(id, version)` primary key (README → Seams); `tests/version-chain.test.ts` ("never rewrites an existing version row", "surfaces a concurrent writer's collision …") |
| `VERSION-CHAIN-006` | A plain update never resurrects a tombstone (it fails `NodeNotFound`); only the explicit `restore` / `restoreVersion` write over one. | `src/version-chain.ts`; `tests/version-chain.test.ts` ("never resurrects a tombstone", "restore — the explicit resurrection surface") |
| `DOC-001` | A stored document is never rewritten, and a changed document is a new hash. `DocumentStore.put` writes a document only when its hash is unseen and is otherwise a no-op returning the same hash; no store method updates or deletes a stored document. So a hash a version row recorded always reads back the document it was written with, and `restoreVersion` restores the reference, not a copy. The hash is SHA-256 over the document's canonical `jsonb` text (README → Seams). | The `DocumentStore` contract in `src/documents.ts`; the store's primary key on the hash with `ON CONFLICT DO NOTHING` (README → Seams); `tests/documents.test.ts` ("put — idempotent, never rewritten (DOC-001)", "restoreVersion restores the old hash …") |
| `PUB-003` | Edits are recorded as appended `(version, action, timestamp, actor)` rows on the node's chain, never rewritten in place, and only the chain operations write them; code that applies an edit on someone's behalf goes through the target's own update. _Partly grounded:_ the apps cite this ID only alongside `READ-009` and `VERSION-CHAIN-001`, and no written definition survives. | `src/version-chain.ts` (the only writer of `VersionRow`); no dedicated test |
| `PUB-005` | A moderated family's `moderationState` is a publication gate: only `approved` is cache-serveable. (That a `pending` or `rejected` row stays readable by its author is the application's operation-layer rule; pulpit does not enforce it.) | `isPubliclyServeable` in `src/publication.ts`; `tests/publication.test.ts` ("the moderationState axis") |
| `PUB-009` | `visibility` (`public` / `followers` / `private`) is an explicit axis, independent of soft-delete and draft. A reference leaf lists only `public` rows unless the viewer holds the view-private rung or the view has no visibility column; an owned row is read through `canViewOwned`. | `referencePrivacyFilter`, `canViewOwned` and `ownedListFilter` in `src/subtype.ts`; `tests/subtype.test.ts` ("canViewOwned", "the reference list predicates") |
| `PUB-010` | `draft` is a binary axis orthogonal to `visibility`: a draft is visible only to its owner and the view-private rung, whatever its visibility, and is never cache-serveable. | `canViewOwned` / `ownedListFilter` in `src/subtype.ts`, `isPubliclyServeable`; `tests/subtype.test.ts` ("a draft narrows even public …"), `tests/publication.test.ts` ("REFUSES a draft …") |
| `READ-009` | A node's history is data: any version can be read back (`getVersion`), listed (`history`) and re-applied as a new version (`restoreVersion`), never by rewinding the chain. In `./subtype`, reading history is gated like a write. | `src/version-chain.ts`, `src/subtype.ts`; `tests/version-chain.test.ts` ("getVersion / restoreVersion — history as data"), `tests/subtype.test.ts` ("the version history is gated like a write …") |
| `PERF-DB-001` | Every read is bounded: `history` is capped at `MAX_HISTORY_LIMIT` (1000), and the store seams specify a `LIMIT` on `head`, `entries`, `get` / `getMany` and `list`. | `src/version-chain.ts`; `tests/version-chain.test.ts` ("is bounded: the limit applies, and is capped"); README → Seams |
| `SEC-INPUT-003` | A list page is capped at `MAX_PAGE_LIMIT` (1000), so no request can drive an unbounded `LIMIT`. | `list` in `src/subtype.ts`; `tests/subtype.test.ts` ("list clamps the page to the cap …") |
| `F-OP-02` | A create is never an upsert: a caller-supplied id that already belongs to a node fails `NodeAlreadyExists` (409), and so does a racing create's version-0 collision. | `src/version-chain.ts`; `tests/version-chain.test.ts` ("… never an upsert over an existing node", "maps a version-0 collision …") |
| `CACHE-AUTH-005` | Nothing that only some viewers may read is served from the KV read-through cache. `isPubliclyServeable` refuses a non-`public` visibility, a draft, a tombstone and a non-`approved` moderation state, plus, by family posture, a missing `visibility` (owned) or an unarrived stamp (publish-gated). **Second spelling:** effect-auth's `Cacheability.publiclyServeable` (with `OwnedAccess.serveableAxes`) states the owned half of this rule, on its `trunk` and unpublished as of 2026-10-08 (release PR effect-auth#177). The two are not yet identical: effect-auth refuses a present `draft` that isn't exactly `false` where pulpit refuses only `true`, and it has no axis for a time-dependent publish stamp. When effect-auth publishes, the rule must converge on one spelling ([#5](https://github.com/thomasfosterau/pulpit/issues/5)) so the two can't drift. | `src/publication.ts`; `tests/publication.test.ts` |
| `PERF-CACHE-004` | The KV read-through resource cache serves anonymous reads, so every mutation writes through it (evicting on delete) and both of its paths apply `isPubliclyServeable`. Cited only in tests here. | `subtypeHandlers` in `src/subtype.ts`; `tests/subtype.test.ts` ("subtypeHandlers — the handlers seam"), `tests/publication.test.ts` |
| `SEC-AUTH-ENUM-001` | In pulpit, the read operations `get`, `getMany` and `list` answer a row the viewer may not see exactly as a missing one: `get` fails `NodeNotFound`, never `Forbidden`, and `getMany` / `list` omit it. The write and history operations (`update`, `restore`, `delete`, `getVersion`, `restoreVersion`) do **not** honour this: their gate (`requireWriter`) answers `Forbidden` for an existing owned row the caller doesn't own, and `NodeNotFound` for a missing one, so they confirm existence to a signed-in caller ([#24](https://github.com/thomasfosterau/pulpit/issues/24)). Edge writes likewise disclose, but only after their gate: a `create` that the gate admits can learn from `EdgeCardinalityExceeded` how many hidden edges a readable node holds, and from `EdgeConflict` that a hidden edge holds a unique key (see `EDGE-001`). **Collision:** website's `SECURITY.md` uses this ID for sign-up email enumeration, and gardeneria's code uses it for both meanings; pulpit uses only the hidden-row meaning. | `get` / `getMany` / `list` in `src/subtype.ts`; `tests/subtype.test.ts` ("a private target refuses a stranger and the anonymous as NotFound, never Forbidden", "list and getMany apply the same facts as get"); for edges, `get` / `list` in `src/edges.ts` (see `EDGE-001`) |
| `EDGE-001` | An edge is readable only if the viewer can read the node at every end, each checked by its own leaf's access rule. An end whose node is missing, hidden or tombstoned hides the edge from every viewer (the view-deleted rung included): `get` fails `EdgeNotFound`, `list` omits it (so a related list omits it too), and a create naming such a node fails `NodeNotFound` before the write gate runs. The list filter and the per-endpoint predicate are one rule in two readings and never disagree. Tombstoning a node deletes none of its edges; restoring it brings them back. pulpit's own rule, introduced with `./edges` (pulpit#52). **What a write discloses, past the gate only** (`create` runs ends → write gate → unique-key collision → cardinality count). (a) `maxEdges` counts hidden edges. Take a readable node with limit `k` and `v` edges the writer can see: a refusal says it holds at least `k − v` hidden edges. Creating `s` edges until a refusal, then deleting them, gives the exact hidden count `h = k − v − s`, and repeating the probe tracks it over time (a side channel). (b) When a family's unique key leaves an end out, `EdgeConflict` says a hidden edge holds that key. **Known limitation** ([#77](https://github.com/thomasfosterau/pulpit/issues/77), owner decision): a tombstoned partner's edge is hidden from everyone, so nobody can delete it, and it still holds its `maxEdges` slot until the partner is restored. | `canViewEndpoint`, `endpointFilter` and `defineEdgeOps` in `src/edges.ts`; `tests/edges.test.ts` ("EDGE-001: the endpoint filter never disagrees …", "EDGE-001: an edge is readable only if every end is", "EDGE-001: a tombstoned end hides its edges …", "known limitation (pulpit#77): …") |
