# Security Policy

## Reporting a vulnerability

Please report security vulnerabilities privately via GitHub's [**Report a vulnerability**](https://github.com/thomasfosterau/pulpit/security/advisories/new) button (Security → Advisories), **not** through public issues.

You can expect an initial response within a few days. Please include a description, reproduction steps, and the affected version.

## Supply-chain hardening

This repository's packages are published with a hardened, automated pipeline designed to resist supply-chain attacks (e.g. self-propagating npm worms that steal credentials and publish trojanized versions):

- **No long-lived npm token.** Publishing is npm trusted publishing (OIDC) from the protected `release` environment: GitHub Actions proves its identity to npm with a short-lived, workflow-bound OIDC token, so there is no `NPM_TOKEN` secret to steal from CI. The publish step is `pnpm publish`, which performs the OIDC exchange itself.
- **Provenance.** Nothing requests [npm provenance](https://docs.npmjs.com/generating-provenance-statements). npm attaches it only when the source repository and the package are both public; this repository is private, so releases carry none today (see [PUBLISHING.md](./PUBLISHING.md#provenance)).
- **Install scripts disabled in the release job.** The release job installs with `--ignore-scripts`, keeps pnpm from re-installing with scripts before a later `pnpm run`, runs only the workspace's own lockfile-pinned `prepare` step explicitly, and publishes with `pnpm publish --ignore-scripts`; the reasons sit beside each setting in [release.yml](.github/workflows/release.yml). CI installs with scripts, but `allowBuilds` in `pnpm-workspace.yaml` names the only packages whose install scripts may run.
- **Pinned actions.** All GitHub Actions are pinned to full commit SHAs, so a hijacked tag cannot inject malicious workflow code.
- **Supply-chain delay.** `minimumReleaseAge` in `pnpm-workspace.yaml` holds a newly published third-party version for one day before pnpm will install it.
- **Least privilege.** Workflows default to `permissions: {}`; each job opts into only the scopes it needs. CI checks out with `persist-credentials: false`.
- **Manual approval gate.** Publishing runs in a protected `release` environment that requires manual approval.
- **Locked dependencies.** Installs use `pnpm install --frozen-lockfile` against the committed `pnpm-lock.yaml`; Dependabot proposes updates for review.

## Release pipeline

The publishing pipeline and its one-time maintainer setup (trusted publisher, protected `release` environment, branch protection) are documented in [PUBLISHING.md](./PUBLISHING.md).

## Existence disclosure by the write gates

The read operations hide a row the viewer may not see (`SEC-AUTH-ENUM-001`). The write and history gates of an owned leaf are a deliberate exception. Each one tells a signed-in caller whether an owned row exists. A reference leaf's gates are not an exception: they hide a row as `get` does ([#101](https://github.com/thomasfosterau/pulpit/issues/101)). This was the owner's decision on [#24](https://github.com/thomasfosterau/pulpit/issues/24#issuecomment-6180404578) (2026-10-14), and it supersedes the decision of 2026-10-08 on that issue to hide such rows. The disclosure is accepted because it needs a signed-in account and a caller must already hold a node id to probe it. Ids the chain store mints (`VersionChainStore.mintId`) are UUIDs, so they can't be guessed; an application that lets callers choose their own ids makes them guessable and weakens this. The gate says only that the row exists. It reveals no content, no visibility and no owner. A change to this rule is a behaviour change with a changeset, and the test pins below change with it.

What each gate answers, from current `trunk` (paths under `packages/pulpit/`):

- **`./subtype`, owned leaf: `requireWriter` in `src/subtype.ts`.** `update`, `restore`, `delete`, `getVersion`, `compare` and `restoreVersion` all run it first, through `defineSubtype`'s `writer` (`getVersion` and `compare` through one shared history-read path, pulpit#82).
  - An anonymous caller gets `Unauthorized` before any row is read. The answer is the same for every id, existing or not, so it discloses nothing. This is decided, not open: the owner chose on [#24](https://github.com/thomasfosterau/pulpit/issues/24#issuecomment-6180623165) (2026-10-14) to keep it, rather than converge on gardeneria's `NotFound` for an anonymous caller on a hidden row (gardeneria#1306 / #1326).
  - A signed-in caller makes the gate read the row's owner (`LeafStore.ownerOf`, the `core.node_owner` record). No owner fails `NodeNotFound`. The owner or the moderate rung passes. Anyone else fails `Forbidden`.
  - The gate never reads the row's visibility, draft or delete state. So a stranger gets `Forbidden` for a `private`, `followers`-only or draft row, and for a tombstone whose owner record remains, exactly as for a `public` one. To a caller the gate refuses, `NodeNotFound` therefore means only that no owner record exists.
  - `getVersion` and `compare` are reads, but they are gated like a write (`READ-009`). A stranger gets `Forbidden` even on a `public` row.
  - Only a caller the gate admits reaches the chain, so only that caller learns the chain's errors: `NodeNotFound` for a tombstone on `update`, `VersionNotFound`, `StaleVersion` and `VersionConflict`.
  - Tests: `tests/subtype.test.ts` pins this behaviour in "the write and history gates confirm existence: a stranger gets Forbidden on every hidden row, the anonymous Unauthorized" (a `private`, `followers`, draft and tombstoned row, and a missing id, on all six operations, `getVersion` and `compare` also at a version no row has), and in "the write gates" ("an owned write admits the owner …", "a missing owner on an owned leaf is NotFound …"), "a stranger cannot write; the owner can …", "the version history is gated like a write …" and "gates first: a caller who may not write learns Forbidden, never the head".
- **`./subtype`, reference leaf: `requireWriter` and `requireCreator`, then `get`'s read check.** Both gates are a pure role check at the corpus-write rung (`atRung`), and neither reads a row. Anonymous gets `Unauthorized` and a signed-in caller below the rung gets `Forbidden`, for any id, so neither discloses anything. Test: "a reference write needs the corpus rung and never loads an owner".
  - For `update`, `restore`, `delete`, `getVersion`, `compare` and `restoreVersion`, `defineSubtype`'s `writer` then reads the row through `visibleRow`, the check `get` itself runs (owner decision on [#101](https://github.com/thomasfosterau/pulpit/issues/101), 2026-10-14). A row that is missing, or that `get` hides from the caller, fails `NodeNotFound` before the chain is reached, so no content is read and nothing is written. `get` hides a row whose visibility isn't exactly `public` (when the view has a visibility column) from a caller without the view-private rung, and a tombstone from a caller without the view-deleted rung (`PUB-009`). So only the view-deleted rung can `restore` a tombstone, or `delete` one (idempotently) without learning `NodeNotFound`; a tombstoned `private` row needs both rungs.
  - A missing id answers `NodeNotFound` on all six operations, `getVersion`, `compare` and `restoreVersion` included (the chain alone would answer `VersionNotFound`), so a hidden row and a missing one are indistinguishable.
  - Only a caller who can `get` the row reaches the chain, and so learns its errors: `NodeNotFound` for a tombstone on `update`, `VersionNotFound` for a version with no row, `StaleVersion` and `VersionConflict`.
  - Because the check is `get`'s own, a change to the reference read rule (such as followers on reference leaves, [#92](https://github.com/thomasfosterau/pulpit/issues/92)) changes these gates with it.
  - The check is against the row's current state. A caller who can `get` the row can read every earlier version through `getVersion`, including one written while the row was `private`.
  - Tests: `tests/subtype.test.ts`, "a reference leaf's write and history gates answer a hidden row as get does (pulpit#101)". It runs every row (`public`, `private`, `followers`, out of the enum, a `null` visibility, a `public` draft, a tombstoned `public` and a tombstoned `private` row, and a missing id) × every caller (anonymous, below the corpus rung, the corpus rung with neither view rung, with view-private only, with view-deleted only, a moderator, an admin) × the six operations (the history reads also at a version no row has, on either side of a `compare`). Each answer must equal what that caller's `get` of the row implies, a refused operation must write nothing, and a refused history read must read no version. "compare: getVersion's gate, then the chain's compare (pulpit#82)" runs every owned row (each visibility, a draft, a tombstone, an ownerless row, a missing id) × every caller × version pair (absent on either side) and requires `compare`'s answer to equal `getVersion`'s for `from` and then `to`.
- **`./subtype`, `requireCreator` on an owned leaf.** Any signed-in account passes. The gate reads no row. But `create` takes a caller-supplied id (`subtypeHandlers` passes the client's input through), and the chain fails `NodeAlreadyExists` when that id already has a head (`F-OP-02`, `src/version-chain.ts`). Any signed-in caller can therefore probe an id for existence through `create`, on an owned leaf, and so can a corpus-rung caller on a reference leaf. This answers for any node, whatever its visibility, delete state or owner. #101 left this unchanged; it covers the five operations on an existing row, not `create`.
- **`./edges`: `create` and `delete` in `src/edges.ts`.** Both check visibility before the write gate runs. `create` reads each end's node first, and an end the viewer can't read, or a tombstoned one, fails `NodeNotFound` for every caller, anonymous included. `delete` answers an edge that is missing or hidden as `EdgeNotFound` (the view-deleted rung reads, and so may delete, an edge whose only hidden end is tombstoned). The gate's `Unauthorized` / `Forbidden` therefore never confirms a hidden node or edge. `rungGate` / `corpusWriteGate` are pure role checks. A gate the application supplies (`EdgeWriteGate`) may read an end's owner.
  - Past the gate, `create` discloses no hidden edge's state ([#93](https://github.com/thomasfosterau/pulpit/issues/93)). The cardinality count reads only edges the caller can read with every end live, so `EdgeCardinalityExceeded` answers a node holding hidden edges as one holding none. A unique-key collision is `EdgeConflict`, carrying only the family's type: under `"fail"` a collision with a hidden edge answers exactly as one with a readable edge; under `"ignore"` only a readable, live edge resolves, and otherwise it is `EdgeConflict`.
  - What remains is accepted (owner decision on #93, 2026-10-14): a limit that holds per caller (a writer who can't read every edge at a node can take it past `maxEdges`), and a collision that says a key is taken, which, where the unique key leaves an end out, tells the writer some hidden edge holds it.
