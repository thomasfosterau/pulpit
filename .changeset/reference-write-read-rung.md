Security fix: on a reference leaf, `update`, `restore`, `delete`, `getVersion` and `restoreVersion` now require the read rung the row demands, as `get` does (pulpit#101). A corpus writer who can't `get` the row (a non-`public` row without the view-private rung, or a tombstone without the view-deleted rung) gets `NodeNotFound`, the same answer as for a missing id, before any content is read or written. Before, the corpus-write rung alone let such a caller read a hidden row's history, rewrite it and revive a tombstone. `getVersion` and `restoreVersion` on a missing reference id now fail `NodeNotFound` rather than `VersionNotFound`. A corpus writer without the view-deleted rung who retries a `delete` of a tombstoned reference row now gets `NodeNotFound` (the wire's 404) instead of the idempotent `alreadyDeleted: true`. Under website's policy (the corpus-write rung from contributor up, the view-private and view-deleted rungs for admins alone), contributors and moderators can no longer edit private reference rows or restore tombstones. Owned leaves are unchanged.
