- [#74](https://github.com/thomasfosterau/pulpit/pull/74) [`80a1fb0`](https://github.com/thomasfosterau/pulpit/commit/80a1fb01cde82a160d464230c58490df04df9d90) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Add `./edges` (and the `Edges` namespace): the edge operations factory, ported from gardeneria's `defineEdgeOpsE`.

  - `defineEdgeOps(definition)` — one edge family's `list` (bounded, ordered by `createdAt` then `id`, with the unpaged total), `get`, `create` (idempotent under `onConflict: "ignore"`, `EdgeConflict` under `"fail"`) and hard `delete`, over an `EdgeStore` seam. Writes gate on `writeGate`: `corpusWriteGate` by default, `rungGate(rung)` for another rung, or a gate on an owned end's owner.
  - Endpoint visibility (`EDGE-001`): an edge is readable only if the viewer can read the node at every end, by that leaf's own access rule. A hidden edge is `EdgeNotFound` from `get` and omitted from `list` and related lists; a create naming a node the viewer can't read fails `NodeNotFound` before the gate. `endpointFilter` (the list arm) and `canViewEndpoint` (the predicate) never disagree.
  - Endpoint lifecycle: a tombstoned end hides its edges from every viewer below the view-deleted rung; restoring the node brings them back.
  - Cardinality: an end's `maxEdges` bounds the edges one node may hold, and a create past it fails `EdgeCardinalityExceeded`. A `maxEdges` that isn't a positive safe integer, or an end alias containing a `.`, throws `EdgeDeclarationError` when the family is declared. Only edges the caller can read whose every end is live count (pulpit#77, pulpit#93).
  - The invariant `EDGE-001` (SECURITY.md). The package README documents taxonomies as a reference leaf plus an edge family.

- [#109](https://github.com/thomasfosterau/pulpit/pull/109) [`4213716`](https://github.com/thomasfosterau/pulpit/commit/4213716928b3e12fc914c350c04cc88912306370) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - `./edges`: the view-deleted rung reads edges to tombstoned ends, and a create no longer discloses hidden edges (pulpit#77, pulpit#93).

  - **The view-deleted rung reads an edge whose only hidden end is tombstoned.** It can `list`, `get` and `delete` the edge, so a moderator can find and remove a retired node's stale edges. An end hidden for any other reason, such as a `private` node below the view-private rung, still hides the edge from that rung. `canViewEndpoint` and `endpointFilter` change together. A create naming a tombstoned node is still `NodeNotFound`, to the rung too.
  - **`maxEdges` counts only the edges the caller can read whose every end is live.** A tombstoned partner frees its slot at once, rather than freezing the node until it is restored. A refusal no longer tells a writer how many hidden edges the node holds. In exchange, the limit holds per caller, so a writer who can't read every edge can take a node past it. A restore can also bring a node past its limit; the node keeps its edges, and the next create there still fails.
  - **The `EdgeStore` seam: `countAt` now takes `{ column, nodeId, where }`.** It counts the edges `list` would match under `where` at that node, over the same joins. The factory passes the viewer's `EDGE-001` filter and every end's liveness. A store that counted with no join must join each end's view, as `list` does.
  - **A collision discloses no more than that the key is taken.** Under `"fail"` a collision with a hidden edge answers exactly as one with a readable edge (`EdgeConflict`, carrying only the family's type); under `"ignore"` only a readable edge whose every end is live resolves to `{ created: false, id }`, and any other collision, the view-deleted rung's with an edge to a tombstone included, is `EdgeConflict`. That generic `EdgeConflict` still says that the key is taken; README → `./edges` → What a write discloses states that residue, which arises only when a family's unique key leaves an end out.

- [#68](https://github.com/thomasfosterau/pulpit/pull/68) [`e7f2f11`](https://github.com/thomasfosterau/pulpit/commit/e7f2f11ccb22afdec92c7e9362e09cf5a1ef75cb) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - Optimistic concurrency: an optional expected-version precondition on every write to an existing node.

  - `./version-chain`: `update`, `restore`, `delete` and `restoreVersion` take an optional `expectedVersion?: bigint | undefined` (the new `Precondition`). It goes in the input for `update` / `restore` and in a trailing argument for `delete` / `restoreVersion`. When the head isn't that version, the write fails the new `StaleVersion` error, which carries the version expected and the head found (`current`), and nothing is written. Without one, behaviour is unchanged.
  - `./subtype`: `defineSubtype`'s `update`, `restore`, `delete` and `restoreVersion`, and `subtypeHandlers`' `update`, `delete` and `restoreVersion`, take the same precondition. Each checks it after the write gate.
  - The check runs against the same head the append extends, so a writer that wins the race in between still surfaces as `VersionConflict` from the store's `(id, version)` key. The `VersionChainStore` seam is unchanged.

- [#136](https://github.com/thomasfosterau/pulpit/pull/136) [`2414470`](https://github.com/thomasfosterau/pulpit/commit/2414470d048f12212e12358f971f023531303014) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - `./filter` gains comparison and literal-set arms (pulpit#113):

  - `gt` / `gte` / `lt` / `lte` over a new `Comparable` (`string | number | Date`), rendered `col > $v` and so on. A string orders by code point (SQL's `"C"` collation), a `Date` by its instant, a number numerically, with `Infinity` and `-Infinity` each equal to itself. A `NULL` or absent column satisfies none, in `evaluate` as in SQL.
  - `anyOf` / `noneOf` over a literal set of `Scalar`s, rendered `col = ANY($values)` / `col <> ALL($values)`. A `NULL` or absent column satisfies neither non-empty arm. An empty `anyOf` is `never`, an empty `noneOf` is `always`, and a set of more than `MAX_SET_VALUES` (1000) values, duplicates counted, is `never` (`SEC-INPUT-003`). A renderer never binds a `NULL` element.

  Outside the contract, `evaluate` fails closed rather than guess at SQL:

  - A column of another type than the comparand, or than any of a literal set's values, is a caller or schema error: PostgreSQL may coerce the parameter or raise, and `evaluate` reads the row as satisfying no `eq`, `ne`, comparison, `anyOf` or `noneOf`. For `ne` this is a change: `ne(col, 1)` was satisfied by a column holding `"2"`, and is no longer.
  - `NaN` (and an invalid `Date`), which PostgreSQL orders equal to itself and above every number. Every constructor, `eq` and `ne` included, returns `never` for a `NaN` or invalid-`Date` comparand, as `anyOf` / `noneOf` do for a set holding a `NaN`, and `evaluate` reads a `NaN` comparand, set element or column as satisfying none of those arms. A renderer must never bind `NaN`. This changes `eq` and `ne`, including the pending `ne` reading (pulpit#75, [#95](https://github.com/thomasfosterau/pulpit/issues/95)): `eq(col, NaN)` and `ne(col, NaN)` now return `never` (`ne(col, NaN)` was satisfied by every non-null row, `NaN` included, where PostgreSQL's `'NaN' <> 'NaN'` is false), and a `NaN` column no longer satisfies `ne(col, v)`.
  - A PostgreSQL timestamp keeps microseconds and a JavaScript `Date` milliseconds, so instants within one millisecond can compare differently.

  `Scalar` is unchanged. A SQL renderer of `ListFilter` must handle the six new node kinds; the rendering contract in the README states them.

- [#141](https://github.com/thomasfosterau/pulpit/pull/141) [`4336d90`](https://github.com/thomasfosterau/pulpit/commit/4336d907adb8babcd53c77ac249fcd795670fba4) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - `list` takes a sort order (pulpit#112). **Seam change:** every `LeafStore` implementation must now honour `orderBy`.

  - `ListRequest` gains an optional `orderBy`: `{ column, direction: "asc" | "desc" }` keys (`ListOrder`). Absent, empty or `null` is today's order, `id` ascending.
  - `defineSubtype` takes an optional per-leaf `sortable` allow-list of view columns; with a list, `id` sorts only if listed, and `[]` admits only the default `id`-ascending order, so any non-empty `orderBy` fails `InvalidListOrder`. An entry that isn't one of the view's `LeafStore.columns` throws the new `SubtypeDeclarationError` when the leaf is declared. **When `sortable` is omitted, every declared view column is sortable**, including columns the resource never shows: a caller can then rank the rows it may already see by any of them, and the 400 below tells it which names are view columns. No hidden row or total is revealed.
  - `defineSubtype`'s `list` checks the order before it reads the viewer or the store. A column that isn't sortable, a direction other than `asc` / `desc`, or input not shaped as an order (no array, a key that isn't an object, a `column` that isn't a string) fails with the new tagged error `InvalidListOrder` (`{ type, column }`), never a defect, so `list`'s error channel (and `SubtypeHandlers.list`'s) gains it. A repeated column is dropped, and each key is rebuilt to just its column and direction.
  - `LeafStore.list`'s query gains the required, already checked `orderBy`. The contract is `ORDER BY <column> ASC|DESC NULLS LAST, …, id ASC`: `NULLS LAST` in both directions, `id` ascending in byte order closing every order (a `uuid`, or a text id under `COLLATE "C"`), and string keys under `COLLATE "C"` (code-point order). A sort key's column must hold a scalar orderable type (text, numeric, boolean, timestamp or bigint), never `json` / `jsonb` or an array. The order never changes which rows match or the total. See README → Seams → `LeafStore`.
  - `makeInMemoryLeafStore` (`./testing`) sorts by that contract. It shares one code-point comparator with `./filter`'s comparison arms, sorts a `bigint` by value, and places `NaN` after every number as PostgreSQL's `float8` does.
