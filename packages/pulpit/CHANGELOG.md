- [#136](https://github.com/thomasfosterau/pulpit/pull/136) [`2414470`](https://github.com/thomasfosterau/pulpit/commit/2414470d048f12212e12358f971f023531303014) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - `./filter` gains comparison and literal-set arms (pulpit#113):

  - `gt` / `gte` / `lt` / `lte` over a new `Comparable` (`string | number | Date`), rendered `col > $v` and so on. A string orders by code point (SQL's `"C"` collation), a `Date` by its instant, a number numerically, with `Infinity` and `-Infinity` each equal to itself. A `NULL` or absent column satisfies none, in `evaluate` as in SQL.
  - `anyOf` / `noneOf` over a literal set of `Scalar`s, rendered `col = ANY($values)` / `col <> ALL($values)`. A `NULL` or absent column satisfies neither non-empty arm. An empty `anyOf` is `never`, an empty `noneOf` is `always`, and a set of more than `MAX_SET_VALUES` (1000) values, duplicates counted, is `never` (`SEC-INPUT-003`). A renderer never binds a `NULL` element.

  Outside the contract, `evaluate` fails closed rather than guess at SQL:

  - A column of another type than the comparand, or than any of a literal set's values, is a caller or schema error: PostgreSQL may coerce the parameter or raise, and `evaluate` reads the row as satisfying no `eq`, `ne`, comparison, `anyOf` or `noneOf`. For `ne` this is a change: `ne(col, 1)` was satisfied by a column holding `"2"`, and is no longer.
  - `NaN` (and an invalid `Date`), which PostgreSQL orders equal to itself and above every number. Every constructor, `eq` and `ne` included, returns `never` for a `NaN` or invalid-`Date` comparand, as `anyOf` / `noneOf` do for a set holding a `NaN`, and `evaluate` reads a `NaN` comparand, set element or column as satisfying none of those arms. A renderer must never bind `NaN`. This changes `eq` and `ne`, including the pending `ne` reading (pulpit#75, [#95](https://github.com/thomasfosterau/pulpit/issues/95)): `eq(col, NaN)` and `ne(col, NaN)` now return `never` (`ne(col, NaN)` was satisfied by every non-null row, `NaN` included, where PostgreSQL's `'NaN' <> 'NaN'` is false), and a `NaN` column no longer satisfies `ne(col, v)`.
  - A PostgreSQL timestamp keeps microseconds and a JavaScript `Date` milliseconds, so instants within one millisecond can compare differently.

  `Scalar` is unchanged. A SQL renderer of `ListFilter` must handle the six new node kinds; the rendering contract in the README states them.

- [#141](https://github.com/thomasfosterau/pulpit/pull/141) [`4336d90`](https://github.com/thomasfosterau/pulpit/commit/4336d907adb8babcd53c77ac249fcd795670fba4) Thanks [@thomasfosterau](https://github.com/thomasfosterau)! - `list` takes a sort order (pulpit#112). **Seam change:** every `LeafStore` implementation must now honour `orderBy`.

  - `ListRequest` gains an optional `orderBy`: `{ column, direction: "asc" | "desc" }` keys (`ListOrder`). Absent, empty or `null` is today's order, `id` ascending.
  - `defineSubtype` takes an optional per-leaf `sortable` allow-list of view columns; with a list, `id` sorts only if listed, and `[]` admits only the default `id`-ascending order, so any non-empty `orderBy` fails `InvalidListOrder`. An entry that isn't one of the view's `LeafStore.columns` throws the new `SubtypeDeclarationError` when the leaf is declared. **When `sortable` is omitted, every declared view column is sortable**, including columns the resource never shows: a caller can then rank the rows it may already see by any of them, and the 400 below tells it which names are view columns. No hidden row or total is revealed.
  - `defineSubtype`'s `list` checks the order before it reads the viewer or the store. A column that isn't sortable, a direction other than `asc` / `desc`, or input not shaped as an order (no array, a key that isn't an object, a `column` that isn't a string) fails with the new tagged error `InvalidListOrder` (`{ type, column }`), never a defect, so `list`'s error channel (and `SubtypeHandlers.list`'s) gains it. The contract is `ORDER BY <column> ASC|DESC NULLS LAST, …, id ASC`: `NULLS LAST` in both directions, `id` ascending in byte order closing every order (a `uuid`, or a text id under `COLLATE "C"`), and string keys under `COLLATE "C"` (code-point order). A sort key's column must hold a scalar orderable type (text, numeric, boolean, timestamp or bigint), never `json` / `jsonb` or an array. The order never changes which rows match or the total.
